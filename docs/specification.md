## 2. 背景与目标

ZFCS Secure SSH 用于为客户端用户和 SOC 设备提供受控的 SSH 证书签发与访问控制能力。本文按正式生产形态定义系统：Broker 与 SSH CA 部署在同一签名节点上，逻辑上划分为对外 API 与校验层，以及本地 OpenSSH 签名执行层；北向接口统一采用 mTLS，授权依据不是独立的应用层 Token，而是自有访问授权 Bundle。该 Bundle 用于承载访问权限说明、调用方身份约束以及与 mTLS 证书链的绑定关系，Broker 必须在验证 mTLS 身份、Bundle 权限范围、请求参数和本地签发策略后，才可复用现有 Smallstep step-ca 初始化的 SSH CA 密钥材料完成签发。用户证书采用短期有效期，用于控制登录行为和会话生命周期；SOC 主机证书采用 3 年长效模式，用于主机身份认证。服务器侧由 `sshd`、生命周期 principal、KRL 和会话过期终止机制共同承担最终执行责任。本文档的目标是明确系统边界、信任边界、身份与密钥管理策略、运行期控制要求、风险和验收标准，使研发、测试、运维和安全评审可以基于同一份规范执行落地和验证。研发联调阶段如仍存在应用层 Bearer Token 机制，应视为过渡兼容方案，不作为正式部署基线。

## 5. 系统概述与资产识别

### 5.1 系统概述

本文中将“Broker”定义为 SSH 证书签发控制面的北向 API 与校验层，但在部署形态上，Broker 与 SSH CA 不是两个跨网独立系统，而是同一签名节点上的一体化组件。该节点复用现有 step-ca 初始化出来的 SSH CA 密钥材料，在本地调用 OpenSSH 原生签发能力完成证书签名，不直接调用远端 step-ca API 作为正式签发路径。Broker 负责暴露受控 HTTPS 接口、验证 mTLS 身份、解析访问授权 Bundle、校验权限范围和请求参数，然后把合格请求交给本地签发执行层完成签名。

核心组件与调用链路如下：

```text
商业/企业证书体系
        |
        |-- 颁发 Broker 服务端 TLS 证书
        |-- 颁发客户端与 SOC 的 mTLS 证书
        v
反向代理 / mTLS 边界
        |
        v
Broker / SSH CA 一体签名节点
   |            \
   |             \__ 审计日志 / 运行日志
   |
   |-- 校验 mTLS 身份、Bundle 权限说明与证书链状态
   |-- 本地访问 SSH User CA / SSH Host CA 私钥材料
   |-- 依据角色、生命周期配置和 TTL 规则签发证书
   |
   +----> 用户侧证书代理 ----> 建立 mTLS、申请用户证书、续签、清理过期证书
   |
   +----> SOC 侧主机证书流程 ----> 建立 mTLS、提交主机公钥、获取 3 年主机证书

用户持用户证书 ------SSH------> 受管服务器 / SOC 的 sshd
                                      |
                                      |-- TrustedUserCAKeys
                                      |-- AuthorizedPrincipalsCommand
                                      |-- allowed_lifecycle_stages
                                      |-- RevokedKeys / KRL
                                      |-- Session Enforcer
```

### 5.2 角色、权限与认证方式

| 角色 | 认证方式 | 主要操作权限 | 权限边界 |
|------|----------|--------------|----------|
| 开发人员 | 开发角色访问授权 Bundle + mTLS | 申请 `development`、`zf_production` 用户证书 | 不得申请其他生命周期配置，不得申请主机证书 |
| 生产操作员 | 生产角色访问授权 Bundle + mTLS | 申请 `zf_production`、`oem_production`、`field_operation`、`end_of_life` 用户证书 | 不得申请 `development`、`claims_warranty` |
| 索赔/保修技术员 | 索赔角色访问授权 Bundle + mTLS | 申请 `claims_warranty`、`field_operation` 用户证书 | 不得申请其他生命周期配置 |
| OEM 集成方 | OEM 角色访问授权 Bundle + mTLS | 申请 `oem_production`、`field_operation` 用户证书 | 不得申请其他生命周期配置 |
| 管理员 | 管理员访问授权 Bundle + mTLS | 申请全部用户证书，执行高风险运维操作 | 必须执行审批与复核要求 |
| 主机注册服务 / SOC 代理 | 主机注册 Bundle + mTLS | 申请主机证书、获取 User CA 公钥 | 不得申请用户证书 |
| SSH 用户 | SSH 用户证书 | 访问受管服务器或 SOC | 受 principal、生命周期、扩展和 KRL 约束 |
| 运维管理员 | 堡垒机/运维账号 | 管理 Broker 主机、反向代理、日志、KRL 分发 | 不得直接绕过审批签发业务证书 |

### 5.3 关键资产识别

| 资产名称 | 位置 | 数据分级 | 泄露或篡改影响 |
|----------|------|----------|----------------|
| SSH User CA 私钥 | CA 主机本地受控目录 | 极高 | 可伪造全部用户证书，导致大范围未授权访问 |
| SSH Host CA 私钥 | CA 主机本地受控目录 | 极高 | 可伪造主机证书，导致主机身份欺骗 |
| Broker TLS 私钥 | 反向代理/CA 主机 | 高 | 可被用于中间人攻击或伪造服务端身份 |
| 访问授权 Bundle | 终端本地安全存储与授权管理平台 | 高 | 可被用于冒用调用角色或绕过正常申请边界 |
| mTLS 客户端私钥 | 终端本地安全存储、SOC 本地或硬件模块 | 极高 | 可被用于伪造受信调用方身份，建立伪造控制面连接 |
| 用户私钥 | 用户终端本地 | 高 | 可被用于冒用用户身份 |
| SOC 主机私钥 | SOC 本地 | 极高 | 可被用于冒充合法设备主机 |
| 用户证书 | 用户终端本地 | 中 | 可被短期滥用，影响 SSH 登录控制 |
| 主机证书 | SOC 或服务器本地 | 中 | 可被用于主机身份冒用 |
| KRL | 服务器/SOC 本地与分发链路 | 高 | 更新失败会导致已吊销证书仍可访问 |
| 生命周期允许列表 | 服务器/SOC 本地 | 高 | 错配会导致越权放行或系统不可用 |
| 审计日志 | Broker 主机、日志平台 | 高 | 丢失或被篡改会破坏追踪与审计能力 |

### 5.4 数据流转路径

1. 用户侧证书代理在本地生成用户私钥，使用访问授权 Bundle 中绑定的 mTLS 凭据与 Broker 建立双向 TLS，仅提交用户公钥、申请参数和必要的授权上下文，Broker 返回用户证书并由代理本地安装。
2. SOC 在本地生成主机私钥，使用主机注册 Bundle 与 Broker 建立双向 TLS，仅提交主机公钥和主机标识信息，Broker 返回 3 年有效期的主机证书并由 SOC 本地安装。
3. Broker 在同一签名节点内完成 mTLS 校验、Bundle 权限判断、生命周期与 TTL 校验，并本地调用 OpenSSH 签发能力完成用户证书或主机证书签名。
4. 用户使用用户私钥和用户证书访问受管服务器或 SOC，`sshd` 根据 CA 锚、生命周期 principal、扩展、KRL 和会话过期规则执行放行或拒绝。
5. Broker 记录签发请求、认证失败、Bundle 校验失败和异常事件，运维侧负责 KRL 更新、日志归档和证书生命周期维护。

## 6. 安全设计目标

| 编号 | 设计目标 | 可验证指标 |
|------|----------|------------|
| G-01 | [证书签发服务] 必须仅允许持有有效访问授权 Bundle 且 mTLS 校验通过的调用方申请与其授权范围一致的证书，在 HTTPS 受保护通道上，验证方式为无证书、错误证书、Bundle 与证书不匹配以及越权角色申请测试均失败。 | 负向接口测试全部失败；审计日志包含失败原因、证书指纹和调用身份。 |
| G-02 | [用户证书] 必须仅允许包含至少一个用户 principal 且恰好一个 `lc:*` 生命周期 principal 的证书用于 SSH 登录，在 `sshd` 认证阶段，验证方式为缺失 principal、多生命周期 principal 场景均被拒绝。 | 认证测试失败；`AuthorizedPrincipalsCommand` 日志可追踪拒绝原因。 |
| G-03 | [用户侧证书代理] 必须在用户证书进入续签窗口时发起续签，在新证书安装成功前禁止删除唯一仍有效的本地证书，验证方式为模拟到期窗口、续签成功和续签失败场景。 | 代理日志包含续签与回退记录；失败时原证书仍可用。 |
| G-04 | [SOC 主机证书] 必须仅允许基于 SOC 本地生成的主机公钥申请 3 年有效期主机证书，私钥禁止上传 Broker，验证方式为接口流量核查和日志核查。 | 签发流量中无主机私钥；默认 TTL 和最大 TTL 均为 1095d。 |
| G-05 | [Broker 与 endpoint 之间的关键链路] 必须仅允许通过 TLS 1.2 及以上的 HTTPS 传输公钥、证书和授权上下文，正式部署下北向接口必须启用 mTLS，非 localhost 场景下禁止明文 HTTP，验证方式为配置检查与访问测试。 | 非 TLS 远程 URL 启动校验失败；无客户端证书或证书不受信的调用被拒绝；反向代理仅暴露 HTTPS。 |
| G-06 | [高风险运维操作] 必须仅允许经审批和双人复核后执行自定义权限签发、KRL 更新、CA 密钥轮换、生命周期允许列表变更，验证方式为审批记录、审计记录和变更单核查。 | 高风险操作具备审批编号、操作人、复核人和执行时间。 |
| G-07 | [受管服务器与 SOC] 必须在生命周期允许列表缺失、KRL 缺失、会话过期控制前提不满足时执行 fail-closed，验证方式为缺失配置测试和启动检查。 | 缺失关键文件时登录失败或服务拒绝启动。 |
| G-08 | [配置变更] 必须对 Bundle 授权模型、mTLS 信任链、TTL 基线、生命周期配置、TLS 证书、`allowed_lifecycle_stages` 和 KRL 更新形成可审计记录，验证方式为配置库记录与审计日志核查。 | 每次变更均可追溯到变更单、提交记录或运维审批。 |

## 7. 网络与信任边界设计

### 7.1 网络区域划分

| 区域名称 | 网段 | 功能 | 安全等级 |
|----------|------|------|----------|
| 证书签发控制区 | 待确认 | 部署 Broker/SSH CA 一体签名节点、SSH CA 密钥、反向代理 | 极高 |
| 运维管理区 | 待确认 | 供运维管理员通过堡垒机管理签名节点和日志 | 高 |
| 设备接入区 | 待确认 | 部署客户端终端、SOC 设备和用户侧证书代理 | 高 |
| 受管 SSH 服务区 | 待确认 | 部署受管服务器与 SOC 的 `sshd` | 高 |
| 审计与监控区 | 待确认 | 日志汇聚、告警、归档、SIEM | 高 |

### 7.2 公网暴露点、第三方连接与管理接口

| 对象 | 类型 | 基线要求 |
|------|------|----------|
| Broker mTLS 入口 | 北向服务入口 | 默认不得直接暴露公网；如因业务需要暴露，必须通过反向代理、IP 白名单、VPN 或等效接入网关保护，并强制客户端证书校验。 |
| 反向代理到 Broker/SSH CA 一体节点 | 服务间调用 | 仅允许本机回环或同主机受控接口访问，禁止跨网段裸露 Broker 监听端口；如由反向代理终止 mTLS，必须把已验证的调用方身份通过受控本地链路传递给 Broker。 |
| 运维 SSH 管理入口 | 管理接口 | 仅允许通过堡垒机或跳板机访问，必须启用多因素认证和来源限制。 |
| 商业 X.509 PKI / 企业证书体系 | 第三方连接 | 用于 Broker 服务端 TLS、mTLS 客户端证书和相关证书状态治理，禁止直接作为 SSH 用户认证源。 |

### 7.3 关键边界控制要求

| 边界 | 允许协议 | 端口 | 身份 | 控制方式 |
|------|----------|------|------|----------|
| 用户侧代理 -> Broker | HTTPS | 443/9443 | 持有有效访问授权 Bundle 的调用方 | TLS 1.2+、mTLS、Bundle 权限校验、源地址限制、请求体大小限制 |
| SOC -> Broker | HTTPS | 443/9443 | 主机注册 Bundle 或管理员 Bundle 持有方 | TLS 1.2+、mTLS、主机标识校验、Bundle 权限校验、日志审计 |
| 用户 -> 受管服务器/SOC | SSH | 22 | 用户私钥 + 用户证书 | `TrustedUserCAKeys`、principal 校验、KRL、会话过期控制 |
| 运维管理员 -> Broker 主机 | SSH/堡垒机协议 | 待确认 | 运维账号 | 堡垒机、MFA、命令留痕、审批关联 |

### 7.4 关键访问路径四问法

| 路径 | 谁能访问 | 通过什么通道 | 访问后能做什么 | 如何被记录和限制 |
|------|----------|--------------|------------------|--------------------|
| 用户侧证书代理 -> `/v1/sign/user` | 持有有效用户角色 Bundle 的客户端 | HTTPS + JSON + mTLS | 申请短期用户证书 | mTLS 校验、Bundle 权限校验、profile 校验、审计日志、请求参数校验 |
| SOC -> `/v1/sign/host` | 持有主机注册 Bundle 的 SOC 或主机注册服务 | HTTPS + JSON + mTLS | 申请 3 年主机证书 | 主机注册 Bundle 校验、主机 principal 校验、审计日志 |
| 用户 -> SOC/服务器 `sshd` | 持有有效用户私钥和用户证书的 SSH 用户 | SSH 证书认证 | 登录主机并执行证书允许的操作 | `AuthorizedPrincipalsCommand`、KRL、会话过期终止、`sshd` 日志 |
| 运维管理员 -> Broker 主机 | 授权运维人员 | 堡垒机/跳板机 | 维护 TLS、日志、KRL、服务配置 | 堡垒机审计、MFA、审批、最小权限 |

### 7.5 访问场景控制要求

- 公网入口：默认禁止 Broker 直接对公网开放；如必须开放，必须通过反向代理、接入网关、来源限制和 HTTPS 加固后暴露。
- 办公网访问：办公网不得直接访问 Broker 监听端口；如需要运维访问，必须经堡垒机、VPN 或专线进入运维管理区。
- 生产网访问：生产环境的客户端和 SOC 仅允许向指定 Broker 域名和端口发起出站访问，不得访问 CA 私钥所在目录或主机管理接口。
- 运维跳转：所有运维管理流量必须经过堡垒机或跳板机，禁止使用共享账号和长期静态白名单。
- 服务间调用：反向代理与 Broker 的调用仅允许本机回环或受控本地接口，禁止把内部 API 直接开放到跨域网络。

## 8. 身份认证、授权与密钥管理设计

### 8.1 身份类型与认证边界

本文所称“访问授权 Bundle”，是指由访问权限说明、调用方身份约束、mTLS 客户端证书链及其绑定关系组成的授权载体。Broker 必须同时验证证书链有效性、证书状态、Bundle 权限说明与请求参数的一致性；任一校验失败时，签发请求必须被拒绝。

| 身份类型 | 认证方式 | 会话策略 | 权限边界 |
|----------|----------|----------|----------|
| 用户角色调用方 | 访问授权 Bundle + mTLS | Bundle 仅用于签发接口调用，不用于 SSH 登录 | 仅可申请其角色允许的用户证书 |
| SOC 主机注册服务 | 主机注册 Bundle + mTLS | 仅用于主机证书申请和 CA 公钥获取 | 不可申请用户证书 |
| SSH 用户 | 用户私钥 + 用户证书 | 用户证书短效；会话过期后强制终止 | 受 principal、生命周期和扩展限制 |
| SOC 主机 | 主机私钥 + 主机证书 | 主机证书长效；到期前更新 | 仅用于主机身份认证 |
| 管理员 | 管理员 Bundle + 运维审批 | 高风险操作必须审批与双人复核 | 允许全部 profile 与高风险运维 |
| 运维管理员 | 运维账号 + 堡垒机/MFA | 运维会话需留痕 | 不得直接跳过签发控制面绕过审批 |

### 8.2 生命周期配置与角色授权矩阵

| 生命周期配置 | principal | 默认 TTL | 允许的核心能力 | 可签发角色 |
|--------------|-----------|----------|------------------|------------|
| `development` | `lc:development` | 12h | 终端、端口转发、Agent 转发 | 开发角色、管理员 |
| `zf_production` | `lc:zf_production` | 4h | 终端 | 开发角色、生产角色、管理员 |
| `oem_production` | `lc:oem_production` | 4h | 终端，可选 `force-command` | 生产角色、OEM 角色、管理员 |
| `field_operation` | `lc:field_operation` | 8h | 终端、端口转发 | 生产角色、索赔角色、OEM 角色、管理员 |
| `claims_warranty` | `lc:claims_warranty` | 2h | 终端，可选 `force-command` | 索赔角色、管理员 |
| `end_of_life` | `lc:end_of_life` | 1h | 终端 | 生产角色、管理员 |
| `custom` | 自定义 | 调用方指定 | 调用方指定 | 仅管理员 Bundle，且必须审批 |

### 8.3 SSH 授权语义

用户证书必须满足以下要求：

- 至少包含一个用户 principal，对应目标 Linux 账户。
- 恰好包含一个生命周期 principal，格式为 `lc:<stage>`。
- 所有用户权限仅通过证书中的 extensions 和 critical options 授予，Broker 和 `sshd` 不得通过隐式默认值额外放权。
- 服务器侧在以下任一条件出现时必须拒绝登录：无生命周期 principal、多生命周期 principal、`allowed_lifecycle_stages` 缺失或为空、KRL 缺失。

证书 extension 与 `sshd` 配置的关系如下：

| 证书 Extension | `sshd` 配置项 | 实际生效规则 |
|---------------|---------------|--------------|
| `permit-pty` | `PermitTTY` | 两者同时允许才生效 |
| `permit-port-forwarding` | `AllowTcpForwarding` | 两者同时允许才生效 |
| `permit-agent-forwarding` | `AllowAgentForwarding` | 两者同时允许才生效 |
| `permit-X11-forwarding` | `X11Forwarding` | 两者同时允许才生效 |
| `permit-user-rc` | 无对应项 | 仅由证书控制 |

critical option 的基线语义如下：

- `force-command=<cmd>`：强制用户仅能执行指定命令。
- `source-address=<CIDR>`：仅允许来自指定源地址段的连接使用该证书。
- `verify-required`：要求具备额外用户验证条件的密钥或设备配合。

### 8.4 高风险操作控制

| 高风险操作 | 审批流程 | 复核要求 | 留痕方式 | 时效控制 |
|------------|----------|----------|----------|----------|
| `custom` 配置签发 | 变更单/工单审批 | 双人复核 | Broker 审计日志 + 变更记录 | 申请单次有效 |
| KRL 更新或批量吊销 | 安全负责人审批 | 双人复核 | KRL 变更记录 + 发布日志 | 发布后立即生效 |
| 生命周期允许列表变更 | 运维与业务负责人审批 | 双人复核 | 配置变更记录 + 主机日志 | 在维护窗口内执行 |
| CA 密钥轮换 | 安全负责人审批 | 双人复核 | 轮换记录 + 审计日志 | 按预定窗口执行 |
| 主机证书 3 年 TTL 基线变更 | 架构与安全联合审批 | 双人复核 | 配置变更记录 + 评审结论 | 仅在版本变更时允许 |

### 8.5 密钥和证书生命周期管理

| 对象 | 生成 | 存储 | 分发 | 轮换/更新 | 吊销/失效 | 权限控制 |
|------|------|------|------|-----------|-----------|----------|
| SSH User CA 私钥 | 由既有 CA 体系生成 | CA 主机本地受控目录/HSM（建议） | 不分发 | 按安全策略轮换 | 轮换后旧证书通过 TTL 与 KRL 控制 | 仅 Broker 运行账户和授权运维可访问 |
| SSH Host CA 私钥 | 由既有 CA 体系生成 | CA 主机本地受控目录/HSM（建议） | 不分发 | 按安全策略轮换 | 通过新证书替换和 KRL 失效控制 | 仅 Broker 运行账户和授权运维可访问 |
| Broker TLS 证书/私钥 | 由商业 X.509 PKI 颁发 | 反向代理/CA 主机 | 仅在 TLS 服务端使用 | 到期前更新 | 证书吊销或替换 | 仅反向代理进程与授权运维可访问 |
| mTLS 客户端私钥 | 由终端本地生成或企业受控下发 | 用户终端、SOC 本地或硬件安全模块 | 不上传 Broker | 到期、泄露或角色变更时轮换 | 吊销相关证书并更新 Bundle | 仅本地受控代理或设备组件可访问 |
| 访问授权 Bundle | 由授权平台或受控流程生成 | 终端本地安全存储、授权平台 | 按角色或设备受控发放 | 权限变更、到期、证书轮换时更新 | 失效、吊销或替换后立即停用 | 禁止共享、禁止脱离角色管理流转 |
| 用户私钥 | 由用户侧证书代理本地生成 | 用户终端本地 | 不上传 Broker | 按设备策略或泄露事件轮换 | 本地删除旧私钥，重新申请证书 | 仅终端用户或本地代理访问 |
| SOC 主机私钥 | 由 SOC 本地生成 | SOC 本地或硬件安全模块 | 不上传 Broker | 到期、泄露或设备替换时轮换 | 重新生成主机密钥并申请新证书 | 仅设备本地受控组件可访问 |
| 用户证书 | Broker 签发 | 用户终端本地 | 通过 HTTPS 返回用户侧 | 进入续签窗口时更新 | 到期后失效，必要时通过 KRL 吊销 | 本地代理负责替换与清理 |
| SOC 主机证书 | Broker 签发 | SOC 本地 | 通过 HTTPS 返回 SOC | 到期前维护窗口更新 | 到期或 KRL 吊销 | 仅设备运维流程可修改 |
| KRL | 授权运维生成 | 服务器/SOC 本地和分发链路 | 由运维向受管主机分发 | 发生吊销事件时更新 | 发布即生效 | 仅授权运维可修改 |

以下行为被明确禁止：

- 在代码、脚本、镜像或公开配置中明文硬编码 Bundle 内容、mTLS 私钥、CA 私钥、密码或私钥口令。
- 通过 Broker、日志、错误响应或 URL 传输用户私钥或 SOC 主机私钥。
- 通过共享 Bundle、共享 mTLS 凭据或共享运维账号跨角色复用权限。

## 9. 数据安全与接口通信设计

### 9.1 数据生命周期控制

| 数据类别 | 采集 | 传输 | 处理 | 存储/备份 | 导出/销毁 |
|----------|------|------|------|-----------|-----------|
| 用户公钥/主机公钥 | 仅采集 OpenSSH 公钥 | HTTPS 传输 | Broker 校验格式、principal、TTL | 不应长期保存原始请求体，审计仅保留必要字段 | 日志与缓存按保留策略清理 |
| 用户证书/主机证书 | Broker 生成 | HTTPS 返回 | 解析、展示、安装 | 用户/SOC 本地保存当前有效证书 | 旧证书到期或替换后清理 |
| 用户私钥/主机私钥 | 本地生成 | 禁止上传 | 仅本地使用 | 仅本地受控存储，不做普通日志备份 | 轮换后安全删除旧版本 |
| 访问授权 Bundle / mTLS 证书 | 由授权平台或证书体系发放 | mTLS 握手 + 受控请求上下文 | Broker 校验证书链、证书状态、权限说明与请求一致性 | 受控存储，禁止写入普通日志 | 到期、吊销或替换后立即删除旧版本 |
| 审计日志 | Broker、`sshd`、代理、本地服务生成 | 发送到日志平台时使用受控链路 | 用于追踪和告警 | 在线与归档分级保留 | 超过保留周期后按策略销毁 |
| KRL | 运维生成 | 受控分发 | `sshd` 加载校验 | 本地文件 + 分发副本 | 新版覆盖旧版，保留发布记录 |

### 9.2 接口与通信基线

| 接口/链路 | 认证方式 | 防重放/幂等 | 超时/重试 | 其他控制要求 |
|-----------|----------|-------------|-----------|----------------|
| `/v1/sign/user` | mTLS + 用户角色 Bundle | 对相同请求参数进行幂等处理；必须校验请求与 Bundle 权限说明是否一致 | 连接超时与读取超时应受控；客户端重试必须避免并发重复申请 | 请求体大小必须受限；必须校验公钥、TTL、principal、profile、证书链状态 |
| `/v1/sign/host` | mTLS + 主机注册 Bundle 或管理员 Bundle | 同上 | 同上 | 主机 principal 必须为合法主机名或 IP，默认 TTL 为 1095d，并校验主机标识与 Bundle 绑定关系 |
| `/v1/ca/user/pubkey` / `/v1/ca/host/pubkey` | mTLS + 有效 Bundle | 不适用 | 受控超时 | 返回内容仅为公钥，不得夹带敏感信息 |
| 用户 SSH 访问链路 | 用户私钥 + 用户证书 | 证书自然过期 + KRL | `sshd` 会话参数控制 | 仅允许证书认证，禁止密码回退 |

### 9.3 数据与接口控制要求

- 北向流量：用户侧代理和 SOC 到 Broker 的申请流量属于北向流量，必须使用 HTTPS，不得走明文 HTTP。
- 东西向流量：反向代理到 Broker 的内部流量应限制在本机回环或同主机受控接口，禁止横向暴露签发服务端口。
- 错误响应：接口错误响应不得包含 Bundle 内容、证书私钥、口令、绝对密钥路径和不必要的系统内部细节。
- 日志暴露：URL、Header、业务日志和错误日志中禁止输出 Bundle 内容、mTLS 私钥、用户私钥、主机私钥和完整证书私有材料。
- 限流要求：签发接口必须按来源 IP、mTLS 身份和 Bundle 授权主体维度具备限流或等效保护能力，防止被高频请求拖垮或滥用。
- 重试要求：客户端或代理重试必须建立在幂等前提之上，禁止以不受控并发方式重复申请证书。

## 10. 运行环境安全与漏洞治理

### 10.1 运行环境安全基线

| 对象 | 安全基线要求 | 暴露面控制 |
|------|--------------|------------|
| Broker/SSH CA 一体节点 | 专用主机或同等受控环境；最小化安装；仅开放必要服务；运行账户对 CA 密钥目录最小可读；Broker 与本地签发执行层必须最小化互信 | 不得直接暴露非必要管理端口；Broker 监听端口不得跨域裸露 |
| 反向代理 | 使用商业 X.509 PKI 证书；强制 TLS 1.2+；强制客户端证书校验；限制请求体大小；配置安全响应头 | 仅暴露 HTTPS 入口；反向代理后端仅指向本机 Broker |
| 受管服务器/SOC | 启用 `TrustedUserCAKeys`、`AuthorizedPrincipalsCommand`、`RevokedKeys`、`ExposeAuthInfo` | 禁止密码认证；禁止不必要的 SSH 能力 |
| 用户侧代理运行环境 | 本地安全存储证书、私钥和 Bundle；日志最小化；续签失败保留现有有效证书 | 禁止把私钥、Bundle 内容或 mTLS 凭据写入普通日志 |
| 审计与监控环境 | 接收 Broker、`sshd` 和代理日志；对关键失败事件告警 | 仅允许受控写入和授权读取 |

### 10.2 漏洞与配置风险治理要求

- 高危漏洞（CVSS >= 9.0）必须在 72 小时内完成修复、隔离或补偿控制；如无法按期修复，应暂停相关签发能力或隔离暴露面。
- 高风险漏洞（7.0 <= CVSS < 9.0）应在 7 天内完成修复或补偿控制。
- 中风险漏洞（4.0 <= CVSS < 7.0）应在 30 天内完成修复或补偿控制。
- 高风险配置错误，例如远程 HTTP、KRL 缺失、密码认证开启、测试 mTLS 凭据或测试 Bundle 未替换，必须在 24 小时内纠正。
- Broker、反向代理和代理程序的依赖组件必须来源于受控仓库或批准源，禁止使用来历不明的镜像、脚本或二进制文件。
- 配置必须纳入版本管理或受控配置分发，禁止长期依赖手工临时修改。
- 生产变更必须具备发布校验和回滚预案，关键配置变更应在维护窗口执行。

## 11. 日志、监控与审计设计

### 11.1 必须记录的事件类型

| 事件域 | 必须记录的事件 |
|--------|----------------|
| Broker 签发面 | 用户证书签发成功、主机证书签发成功、认证失败、越权 profile 申请、参数校验失败、证书解析失败 |
| 服务器执行面 | 登录成功、登录失败、principal 校验失败、生命周期阶段拒绝、KRL 命中、Session Enforcer 终止会话 |
| 运维与密钥 | KRL 更新、生命周期允许列表变更、TLS 证书更新、mTLS 证书更新、Bundle 权限模型更新、CA 密钥轮换 |
| 代理运行面 | 续签成功、续签失败、证书替换、过期证书清理失败、到期窗口告警 |

### 11.2 日志字段要求

每条安全相关日志至少包含以下字段：

- 时间戳
- 操作者或调用身份
- 源 IP
- 目标对象
- 操作类型
- 操作结果

建议附加字段如下：

- 角色、Bundle 标识或客户端证书指纹
- `key_id`
- principal 列表
- 生命周期 profile
- 错误码
- 主机名或设备标识

### 11.3 日志保留、访问控制与告警

- 在线日志保留周期建议不少于 180 天；归档保留周期建议不少于 365 天。如企业基线更严格，应以更严格要求为准。
- 日志仅允许安全团队、审计团队和授权运维人员读取，普通业务调用方不得读取审计日志。
- 所有主机必须与统一时间源同步，推荐使用 NTP 或 Chrony，防止审计时间线失真。

| 告警项 | 触发条件 | 响应要求 |
|--------|----------|----------|
| Broker 认证失败 | 5 分钟内连续失败达到阈值 | 排查暴力尝试、mTLS 证书失效、Bundle 异常或脚本错误 |
| 越权 profile 申请 | 任意一次越权申请 | 立即审查调用方身份、Bundle 权限说明和证书使用情况 |
| 用户代理续签失败 | 到期窗口内连续失败 | 在证书到期前完成人工介入 |
| SOC 主机证书临期 | 距离到期 30 天、15 天、7 天 | 启动维护窗口和更新流程 |
| KRL 分发失败 | 任意一次分发失败或版本不一致 | 立即人工干预，确保吊销生效 |
| Session Enforcer 失败 | 任意一次前提检查失败或执行失败 | 立即修复，避免过期会话持续有效 |

日志中禁止包含以下内容：

- 访问授权 Bundle 明文
- mTLS 私钥
- 用户私钥或主机私钥
- 口令、私钥口令
- 不必要的完整证书内容或内部敏感路径

## 12. 风险分析、验收标准与运维要求

### 12.1 风险分析

| 风险点 | 攻击路径 | 影响 | 现有控制 | 补充控制 | 责任方 | 优先级 |
|--------|----------|------|----------|----------|--------|--------|
| 访问授权 Bundle 或 mTLS 调用凭据泄露 | 攻击者获取有效 Bundle 或客户端证书及其私钥后冒用合法调用方访问签发接口 | 越权申请证书，扩大 SSH 访问面 | mTLS、Bundle 权限校验、审计日志 | 凭据托管到密钥平台、短周期证书、吊销机制、按源地址限流与限制 | 平台安全/运维 | 高 |
| Broker/SSH CA 一体节点被攻陷或 SSH CA 私钥泄露 | 攻击者控制签名节点或私钥目录权限配置错误 | 可伪造用户或主机证书，影响全局信任 | CA 私钥仅本地访问、同机回环调用、上层 PKI 治理 | HSM/KMS、专用服务账户、主机加固、EDR/FIM、双人运维 | 安全架构/运维 | 高 |
| SOC 长效主机证书被滥用 | SOC 主机私钥泄露且 3 年证书仍有效 | 设备主机身份长期被冒用 | 本地生成私钥、不上传 Broker | TPM/SE 存储、主机私钥轮换、泄露后立即更新 KRL | 设备平台/运维 | 高 |
| 用户侧证书代理失效 | 本地代理续签失败或定时任务失效 | 用户证书到期导致业务中断 | 短期证书、代理本地日志 | 到期窗口告警、失败回退、集中监控 | 终端平台/运维 | 中 |
| KRL 分发延迟 | 已吊销证书未及时分发到受管服务器或 SOC | 已撤销证书仍可继续访问 | `RevokedKeys`、KRL 机制 | 版本一致性检查、分发告警、运维巡检 | 运维/SOC | 高 |
| 生命周期允许列表错配 | `allowed_lifecycle_stages` 配置不当 | 越权放行或 fail-closed 导致登录中断 | `AuthorizedPrincipalsCommand`、fail-closed | 配置变更审批、上线前核查、回滚预案 | 运维/安全 | 中 |

对高优先级风险，以下控制项为强制项：

- 访问授权 Bundle 和 mTLS 调用凭据必须受控存储、可轮换、可吊销，不得明文硬编码或共享。
- SSH CA 私钥必须限制访问主体，禁止跨域分发，必须具备轮换和审计能力。
- SOC 主机私钥泄露事件必须触发重新生成密钥、更新主机证书和发布 KRL。
- KRL 分发失败必须触发告警并在规定时限内恢复一致性。

### 12.2 残余风险

| 残余风险 | 接受原因 | 重新评估触发条件 |
|----------|----------|------------------|
| SOC 主机证书有效期为 3 年，泄露后理论暴露窗口较长 | 该设计用于降低频繁更新成本，前提是主机私钥本地受控且具备吊销路径 | 发生私钥泄露、设备平台改用 TPM/SE、更新窗口策略变化 |
| 用户侧证书代理实现方式尚未统一 | 不同终端平台运行环境差异较大，需分平台实施 | 代理载体冻结、终端平台切换或自动化要求提升 |
| Broker 当前依赖本地 CA 密钥材料 | 现阶段沿用 step-ca 已有资产可快速落地 | 引入远程签名、HSM、KMS 或跨域部署需求 |

### 12.3 验收标准

| 检查对象 | 检查方式 | 通过标准 |
|----------|----------|----------|
| Broker 暴露面 | 端口核查、反向代理配置核查 | 仅暴露 HTTPS 入口；内部 Broker 端口不对跨域网络开放 |
| TLS 边界 | URL、证书链、协议核查 | 非 localhost 场景仅允许 HTTPS；Broker 服务端 TLS 和客户端 mTLS 证书均来自受控证书体系 |
| 用户签发接口鉴权 | 正向与负向接口测试 | 无 mTLS 证书、错误证书、Bundle 与证书不匹配、越权 Bundle 请求均失败 |
| 主机签发接口鉴权 | 正向与负向接口测试 | 仅主机注册 Bundle 或管理员 Bundle 可申请主机证书 |
| 生命周期鉴权 | SSH 登录验证 | 缺失 `lc:*`、多个 `lc:*`、不允许阶段登录全部失败 |
| 用户证书续签流程 | 代理模拟测试 | 进入续签窗口时可成功续签；失败时不会删除唯一有效证书 |
| SOC 主机证书默认有效期 | 配置检查、接口响应核查 | Host 默认 TTL 和最大 TTL 为 1095d（3 年） |
| 会话过期终止 | Session Enforcer 验证 | 用户证书过期后已建立会话被终止 |
| KRL 生效 | 吊销测试 | 被吊销证书在目标服务器和 SOC 上均被拒绝 |
| 网络访问路径 | 访问路径核查、抓包、ACL 核查 | 仅存在规范定义的 HTTPS 和 SSH 路径，无额外直连通道 |
| 日志留痕 | 日志字段检查 | 日志包含时间、身份、源 IP、目标对象、结果；不包含 Bundle 内容和私钥 |
| 配置变更审计 | 变更单与日志核查 | Bundle 授权模型、TTL、KRL、生命周期配置和证书信任链变更均可追溯 |

### 12.4 运维要求

| 运维领域 | 要求 |
|----------|------|
| 账号管理 | Bundle 和 mTLS 凭据按角色或设备分配，离岗、停用或权限变更时立即回收；运维账号禁止共享。 |
| 日常巡检 | 每日核查 Broker 服务状态、TLS 与 mTLS 证书有效期、KRL 分发状态、代理续签失败事件。 |
| 告警响应 | 高优先级告警必须在定义时限内响应并记录处置过程。 |
| 权限回收 | 生命周期允许列表、Bundle、mTLS 凭据和运维权限变更后必须同步回收旧权限。 |
| 备份恢复 | 仅备份必要配置、日志和 KRL；私钥备份必须受控并具备恢复演练。 |
| 应急联动 | 私钥泄露、Bundle 或 mTLS 凭据泄露、异常签发、KRL 分发失败应触发安全、运维和业务方联动。 |

## 重点风险与优先整改项

1. 应优先落地用户侧证书代理的续签窗口、失败回退和本地日志标准，否则用户短期证书策略无法稳定运行。
2. 应优先确认访问授权 Bundle 与 mTLS 凭据的签发、托管、轮换和吊销机制，否则签发控制面仍存在较高的身份冒用风险。
3. 应优先明确 SOC 主机私钥的保护介质与泄露处置流程，否则 3 年长效主机证书的风险无法闭环。
4. 应优先建立 KRL 分发一致性检查和告警，否则吊销链路无法作为可靠控制项。
5. 应优先冻结生产环境网络区划和运维访问路径，以便完成正式验收和暴露面核查。
